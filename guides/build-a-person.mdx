---
title: "Build a specific person"
description: "Build a simulated person, or a small group, from a brief, real material, or both: applied at once, then answer, correct, add later and edit in words."
mode: "how-to"
---

You want a [person](/concepts/people) who fits a real audience: not a row pulled from the shared pool, but one built to your brief and grounded in material you already have. This guide builds that person from a description, [sources](/concepts/source) (transcripts, emails, surveys, PDFs, images, audio), or both, on either surface, step by step.

A build makes simulated people; it does not turn the output into a real human. A person built from a real transcript is closer to the mark than one built from a prompt alone, but it is still simulation. Frame the findings the same way.

## Before you start

- An active workspace. The CLI reads it from your [active context](/concepts/active-context); MCP takes a `workspace_id`. Built people land in that workspace.
- A brief, material, or both.
- A rights statement, whenever you hand in a file or add anything to an existing person (whatever the words setting), and whenever you use someone's own words (`own_words`): why you may share it (the people agreed, it is public, it comes from your work with them, or it is your own). A typed description for new people, used as inspiration, needs none. An agent asks the user; it never chooses one.

<Note>
Built people count toward your plan's custom-person cap, which is separate from the per-run credit pool. See [credits and limits](/concepts/credits-and-limits).
</Note>

Handing material in is the approval: what ish reads is applied at once, with nothing to accept. Three rules hold on every surface. A real person's material handed in through the CLI, MCP or the in-app assistant waits for one confirm that only the ish app gives. Whether a person is real is answered only in the ish app; an agent gets the question and a link. An exact value is set with `ish person update` or `person_update`, and a description changes only through a build.

<Steps>
<Step title="Build">
Hand in a brief, material, or both. Say who they are only as you know it: `made_up` for someone you invented, `real_person` for a real person. With files, with anything added to an existing person, or to use someone's own words (`own_words`), say why you may share them.

<CodeGroup>
```bash CLI
# From a brief
ish person build --brief "A Malmö accountant with a toddler" --wait

# From material about a real person
ish person build ./interview.m4a --who real_person --basis agreed \
  --brief "Priya, the night nurse I interviewed" --wait
```

```text MCP
person_build(
  workspace_id="w-6ec",
  brief="A Malmö accountant with a toddler",
)

person_build(
  workspace_id="w-6ec",
  brief="Priya, the night nurse I interviewed",
  sources=[{"path": "https://example.com/interview.m4a"}],
  who="real_person",
  rights_basis="agreed",
)
```
</CodeGroup>

The build waits until the material is read, by default on MCP (`wait=True`) and with `--wait` on the CLI. It returns the people with what was applied to each, any open questions, and what was refused or skipped (a file that could not be read, a category ish does not store).
</Step>

<Step title="A real person: one confirm in the app">
A real person's material handed in through the CLI or MCP is read and structured, then waits for one confirm in the ish app before anything is applied. The build returns the app link (`app_url`, with `waits_for_user_in_app` on MCP; exit code 2 with the link on the CLI). Give the link to the user; they can confirm many people at once. Material that is not confirmed within 30 days is discarded with its files. A hand-in made in the app itself applies at once.
</Step>

<Step title="Answer">
ish asks only where a wrong guess would mix people up: which voice is this person, which of your people is this about, are these the same person, is this a real person. Each question holds back only what depends on it; everything else is already applied. Ask the user and pass the answer.

<CodeGroup>
```bash CLI
ish person review <import-id>
ish person review <import-id> --answer <question-id>=<answer> --wait
```

```text MCP
person_review(workspace_id="w-6ec", import_id="…")
person_review(workspace_id="w-6ec", import_id="…", action="answer", question_id="…", answer="…")
```
</CodeGroup>

"Is this a real person?" is not among the questions an agent answers: the CLI and MCP return it with the app link, and the user answers it in the app. An answer about a real person, given through the CLI or MCP, then waits for the same one confirm.
</Step>

<Step title="Correct afterwards">
Read what a hand-in changed, then edit a value, leave one item out, or undo the whole hand-in. Undo restores the earlier values and keeps the history; through the CLI or MCP it never removes a person. On a real person, editing, leaving out and undoing happen in the ish app; the CLI and MCP give you the link.

<CodeGroup>
```bash CLI
ish person review <import-id>
ish person review <import-id> --edit <item-id>=35
ish person review <import-id> --leave-out <item-id>
ish person review <import-id> --undo --yes
```

```text MCP
person_review(import_id="…", detail=True)
person_review(import_id="…", action="edit", item_id="…", value="35")
person_review(import_id="…", action="leave_out", item_id="…")
person_review(import_id="…", action="undo")
```
</CodeGroup>

A left-out item can be put back (`--restore` / `action="restore"`). A value you typed yourself is never overwritten by later material: what the material says instead is listed as kept back, and one act uses it (`--use-instead` / `action="use_instead"`).
</Step>

<Step title="Add later">
As new material arrives, hand it to the same person. It is applied the same way.

<CodeGroup>
```bash CLI
ish person build --to p-d4e ./meetings/2026-06-12.vtt --basis work \
  --brief "Steering meeting; she is Speaker 2." --wait
```

```text MCP
person_build(
  workspace_id="w-6ec",
  person_id="p-d4e",
  sources=[{"path": "https://example.com/2026-06-12.vtt"}],
  rights_basis="work",
)
```
</CodeGroup>
</Step>

<Step title="Edit in words">
A change in words is a build with a person: it is applied, and what changed is listed like any hand-in, with undo.

<CodeGroup>
```bash CLI
ish person build --to p-d4e --brief "Make her ten years older" --basis own --wait
```

```text MCP
person_build(workspace_id="w-6ec", person_id="p-d4e", brief="Make her ten years older", rights_basis="own")
```
</CodeGroup>
</Step>
</Steps>

## After the build

Each person gets a short alias, `p-` on both surfaces (for example `p-d4e`). Hand those ids straight to a run, and read the whole person, every value with where it came from and every file with what it gave:

<CodeGroup>
```bash CLI
ish person get p-d4e --profile --sources
ish study run --person p-d4e
```

```text MCP
person_get(workspace_id="w-6ec", person_id="p-d4e", include=["profile", "sources"])
study_run(study_id="s-1a2", audience={"person_ids": ["p-d4e"]})
```
</CodeGroup>

## When a build is not the right tool

| You want | Reach for |
|---|---|
| People from a brief, material, or both | `ish person build` / `person_build` (this guide) |
| An exact value on a person | `ish person update` / `person_update` |
| An exact Person from a JSON spec, no model involved | `ish person create --file` |
| People that already exist in a pool | Sample from the pool ([people and panels](/concepts/people)) |
