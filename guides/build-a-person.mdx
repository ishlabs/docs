---
title: "Build a specific person"
description: "Build a simulated person, or a small group, from a brief, real material, or both; answer, accept, add later and edit in words."
mode: "how-to"
---

You want a [person](/concepts/people) who fits a real audience: not a row pulled from the shared pool, but one built to your brief and grounded in material you already have. This guide builds that person from a description, [sources](/concepts/source) (transcripts, emails, surveys, PDFs, images, audio), or both, on either surface, in five steps.

A build makes simulated people; it does not turn the output into a real human. A person built from a real transcript is closer to the mark than one built from a prompt alone, but it is still simulation. Frame the findings the same way.

## Before you start

- An active workspace. The CLI reads it from your [active context](/concepts/active-context); MCP takes a `workspace_id`. Built people land in that workspace.
- A brief, material, or both.
- With material: why you may share it (the people agreed, it is public, it comes from your work with them, or you made it). Ask the person whose material it is; an agent never chooses one.

<Note>
Built people count toward your plan's custom-person cap, which is separate from the per-run credit pool. See [credits and limits](/concepts/credits-and-limits).
</Note>

Two rules hold on every surface. Whether a person is real is answered only in the ish app; an agent gets the question and a link. An exact value is set with `ish person update` or `person_update`, and a description changes only through a build.

<Steps>
<Step title="Build">
Hand in a brief, material, or both. Say who they are only as you know it: `made_up` for someone you invented, `real_person` for a real person. With files, say why you may share them.

<CodeGroup>
```bash CLI
# From a brief
ish person build --brief "A Malmö accountant with a toddler" --wait

# From material about a real person
ish person build ./interview.m4a --who real_person --basis agreed \
  --brief "Priya, the night nurse I interviewed" --wait
```

```text MCP
person_build(
  workspace_id="w-6ec",
  brief="A Malmö accountant with a toddler",
)

person_build(
  workspace_id="w-6ec",
  brief="Priya, the night nurse I interviewed",
  sources=[{"path": "https://example.com/interview.m4a"}],
  who="real_person",
  rights_basis="agreed",
)
```
</CodeGroup>

The build waits for the draft by default on MCP (`wait=True`) and with `--wait` on the CLI. It returns a draft: each person, what an accept would take, and anything waiting on you.
</Step>

<Step title="Answer">
When ish needs to know something first (who is this voice, are these the same person), the draft carries questions. Ask the user each one and pass the answer.

<CodeGroup>
```bash CLI
ish person review <import-id>
ish person review <import-id> --answer <question-id>=<answer> --wait
```

```text MCP
person_review(import_id="…")
person_review(import_id="…", action="answer", question_id="…", answer="…")
```
</CodeGroup>

"Is this a real person?" is not among the questions an agent answers: the CLI and MCP return it with the draft's link, and the user answers it in the app.
</Step>

<Step title="Accept, or look through first">
Read the draft with the user, then accept. A made-up person's draft can be accepted from the CLI or MCP. A real person's draft is accepted only in the ish app; the CLI and MCP give you the link, and on such a draft they answer, edit and leave out nothing either.

<CodeGroup>
```bash CLI
ish person review <import-id> --all
ish person review <import-id> --edit <item-id>=35 --accept
```

```text MCP
person_review(import_id="…", detail=True)
person_review(import_id="…", action="accept")
```
</CodeGroup>

To skip the look-through for made-up people, pass `--accept` (CLI) or `accept=True` (MCP) on the build: it accepts each made-up person that nothing waits on, one by one, and leaves the rest as a draft.
</Step>

<Step title="Add later">
As new material arrives, hand it to the same person.

<CodeGroup>
```bash CLI
ish person build --to p-d4e ./meetings/2026-06-12.vtt --basis work \
  --brief "Steering meeting; she is Speaker 2." --wait
```

```text MCP
person_build(
  workspace_id="w-6ec",
  person_id="p-d4e",
  sources=[{"path": "https://example.com/2026-06-12.vtt"}],
  rights_basis="work",
)
```
</CodeGroup>
</Step>

<Step title="Edit in words">
A change in words is a build with a person: it ends in a draft that shows what changes, which you accept as above.

<CodeGroup>
```bash CLI
ish person build --to p-d4e --brief "Make her ten years older" --wait
```

```text MCP
person_build(workspace_id="w-6ec", person_id="p-d4e", brief="Make her ten years older")
```
</CodeGroup>
</Step>
</Steps>

<Note>
Until a workspace has drafts, words handed to an existing person are stored as a note to approve, and nothing is edited. A build that creates people makes them at once.
</Note>

## After the build

Each person gets a short alias, `p-` on both surfaces (for example `p-d4e`). Hand those ids straight to a run, and read the whole person, every value with where it came from and every file with what it gave:

<CodeGroup>
```bash CLI
ish person get p-d4e --profile --sources
ish study run --person p-d4e
```

```text MCP
person_get(workspace_id="w-6ec", person_id="p-d4e", include=["profile", "sources"])
study_run(study_id="s-1a2", audience={"person_ids": ["p-d4e"]})
```
</CodeGroup>

## When a build is not the right tool

| You want | Reach for |
|---|---|
| People from a brief, material, or both | `ish person build` / `person_build` (this guide) |
| An exact value on a person | `ish person update` / `person_update` |
| An exact Person from a JSON spec, no model involved | `ish person create --file` |
| People that already exist in a pool | Sample from the pool ([people and panels](/concepts/people)) |
