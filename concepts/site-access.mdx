For most studies ish reaches the artifact directly. You point an
[iteration](/concepts/iteration) at a public URL, attach a file, or wire up a
chatbot endpoint, and the simulation runs. Site access is for the case where the
URL is not reachable as-is: a staging gate, a preview link behind a token, a page
that only renders after a login.

Site access lives on a **site** inside your [workspace](/concepts/workspace). A
site is one web site or one native app, and it holds its own access. You configure
how ish should get past a site's gate once, and every study whose URL (or app)
belongs to that site reuses it. A workspace can hold several sites, each with its
own access. Site access is an `interactive`-study concern, not a media or chatbot
one.

## When you need it

An `interactive` study sends simulated people through a real cloud browser pointed
at the iteration's URL. If that browser cannot load the page, the simulation has
nothing to react to. Site access closes that gap for the three common ways a URL is
gated:

- A staging site behind **HTTP basic auth** (the browser dialog that wants a
  username and password before any page loads).
- A preview link gated on a **session cookie**: a Vercel preview, a Lovable
  preview, anything that checks for a token cookie and otherwise shows a wall.
- A site behind a **login form**: a real sign-in page the participant fills in and
  submits to reach the part of the product under test.

If the URL is already public, you do not need site access at all. A study against
a live marketing page or a published prototype just runs.

## Public versus gated

ish does not require you to declare that a public site is public. The default is
that no credentials are attached and the browser loads the URL as any anonymous
visitor would. The one thing the public method adds is an explicit affirmation:
you are telling ish, on the record, that this site needs nothing. Tools and UI
read that flag to stop nudging you about credentials on a site you have already
confirmed is open.

That makes "public" a real, separate state, not the absence of configuration:

| State | What it means | What ish does |
|---|---|---|
| Nothing configured | No credentials, no affirmation | Loads the URL anonymously; may still prompt "does this need access?" |
| Public affirmed | You confirmed the site is open | Loads anonymously; stops prompting for that site |
| A method configured | basic auth, cookie, or login is set | Applies that method when a study runs on the site |

The two are mutually exclusive by design: a site you just handed a password to is
not one you are also calling open. Saving any credential (basic auth, cookie, or
login) withdraws the site's public affirmation, and affirming a site public is
refused while it still holds a credential.

## The four methods

Each method matches how the gate actually works. Pick the one that describes the
wall in front of your URL. Every method belongs to one site.

<AccordionGroup>
  <Accordion title="Basic auth" icon="lock">
    HTTP basic auth: the credentials the browser sends before any page renders,
    the username and password behind the native browser prompt. Configured as a
    username plus a password. ish presents them to the origin the run opens, so
    the page loads.
  </Accordion>
  <Accordion title="Session cookie" icon="cookie">
    A cookie ish sets on the origin the run opens, before the first page load, for
    sites that gate on a token rather than a prompt: a Vercel preview, a Lovable
    preview, a staging link behind a bypass cookie. Configured as a cookie name
    plus a value. Every cookie carries an expiry; once it passes, ish refuses the
    run (`session_cookie_expired`) until you register a fresh one.
  </Accordion>
  <Accordion title="Login form" icon="key">
    Username and password for a real sign-in form. Unlike basic auth and cookie,
    these are not handed to the browser up front: the participant types them into
    the site's own login page if it meets one during the task, the way a real
    person signs in. The login belongs to its site, so only runs on that site see
    it. It is the only method a native app site takes.
  </Accordion>
  <Accordion title="Public" icon="globe">
    Not a credential. An affirmation that the site needs no access at all, which
    silences the prompt asking whether it does.
  </Accordion>
</AccordionGroup>

## Sites and hosts

A **site** is a place your studies go: a web site, identified by its host, or a
native app, identified by its app artifact (the bundle id or path the iteration
stores). A site is created the first time you give it access, and is named after
its host or app.

A web site answers on one or more **hosts**. Its first host is its address; add
others when the same site answers somewhere else, for example `shop.se` beside
`shop.com`, a sign-in subdomain such as `auth.shop.com`, or `localhost:3000`
for a local build. `www` and the bare domain are already the same host, so you
never add both. A host belongs to one site only.

A study's URL picks its site by host, and the run uses that site's access and
never another site's:

- **Basic auth and the cookie go to exactly one origin**: the one the run opens.
  That is the study URL's origin, or, for a localhost site, the tunnel that
  [`ish connect`](/cli/generated/connect) opens for it, so a local site keeps its
  access through the tunnel. They are never sent to every host of the site;
  hosts only decide which site a study belongs to.
- **A run on a host outside its site gets none of that site's access**, and
  dispatch warns.
- **A study on a host no site covers runs with no access.** When other sites in
  the workspace do hold access, `ish study run` warns at dispatch, which is the
  tell for a typo or a host you have not added yet.

You rarely have to spell the site out. Name it by URL (`--origin`, created on
first use), by name (`--site`), or by app (`--app`); with none of them, ish uses
the site for the workspace's `base_url`. Clearing access and editing hosts always
need the site named. A write that makes a new site says so (`created: true`), and
lists the other sites that already hold access, so a mistyped origin shows up
straight away instead of as a run that silently loads without credentials.

## Where the credentials live

Credentials (passwords and cookie values) are stored encrypted at rest. Neither the
CLI nor the MCP server ever reads one back: both report only which methods each
site has. A site's hosts are ordinary workspace data, so a status read lists every
site with its hosts and methods, plus the hosts your browser studies target that no
site covers yet.

<Warning>
  The old secret names `BASIC_AUTH_*`, `SESSION_COOKIE_*`, and `LOGIN_*` stay
  reserved. The plain secret commands refuse them and point you here. Always go
  through the site-access surface.
</Warning>

## Reading and changing it

Both developer surfaces expose the same configure verbs, a hosts edit, a status
read, and a clear. The status read never returns a secret value. The example below
shows the parity across surfaces, not a procedure to follow in order.

<CodeGroup>

```bash CLI
# Every site: hosts, methods, cookie expiry
ish workspace site-access status

# A staging gate (basic auth); the site is created on first use
ish workspace site-access basic-auth --origin https://staging.example.com \
    --username alice --password hunter2

# A preview cookie (Vercel, Lovable, etc.) on an existing site
ish workspace site-access cookie --site preview.example.app \
    --name session --value abc123 --expires-at 2026-12-31T08:00:00Z

# A login form the participant fills in, for the base_url site or an app
ish workspace site-access login --username demo --password demo
ish workspace site-access login --app com.example.app --username demo --password demo

# Affirm a site public to silence the prompt
ish workspace site-access affirm-public --origin https://shop.com

# More hosts for one site (--add appends, --set replaces)
ish workspace site-access hosts --site shop.com --add shop.se
ish workspace site-access hosts --site shop.com --set auth.shop.com,localhost:3000

# Clear one method, or everything, from a named site
ish workspace site-access clear cookie --site preview.example.app
ish workspace site-access clear all --origin https://staging.example.com
```

```python MCP
# Every site and its access
site_access_get(workspace_id="w-6ec")

# Configure one method (polymorphic on `method`); target is one of
# origin, site, or app_artifact (none: the workspace base_url)
site_access_set(workspace_id="w-6ec", method="basic_auth",
                origin="https://staging.example.com",
                username="alice", password="hunter2")
site_access_set(workspace_id="w-6ec", method="cookie",
                site="preview.example.app", name="session", value="abc123")
site_access_set(workspace_id="w-6ec", method="login",
                app_artifact="com.example.app",
                username="demo", password="demo")
site_access_set(workspace_id="w-6ec", method="public",
                origin="https://shop.com")

# Hosts replace the site's extra hosts (pass the current ones to add)
site_access_set(workspace_id="w-6ec", method="hosts", site="shop.com",
                hosts=["shop.se", "auth.shop.com", "localhost:3000"])

# Clear one method, or all of them, from a named site
site_access_clear(workspace_id="w-6ec", method="cookie",
                  site="preview.example.app")
site_access_clear(workspace_id="w-6ec", method="all",
                  origin="https://staging.example.com")
```

</CodeGroup>

<Tip>
  Keep secrets out of your shell history. On the CLI, pass `-` for `--password` or
  `--value` and pipe the value on stdin:
  `printf %s "$STAGING_PW" | ish workspace site-access basic-auth --username alice --password -`.
</Tip>
