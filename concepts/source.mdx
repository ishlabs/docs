A **source** is material about people that you hand to a build: an interview transcript, a call recording, a survey export, a support email, a screenshot, a PDF. ish reads it once per workspace and keeps it on each [Person](/concepts/people) it feeds, so the same file handed in twice in one workspace is one source. This page is the mental model: what a source is, what it gives a Person, and how it lives over time. For exact flags and parameters, follow the links to the [CLI](/cli/generated/source) and [MCP](/mcp/generated/tools-person) reference.

## What a source does

A brief alone produces a plausible Person. A brief plus a source produces a Person pinned to material. The build reads the file and turns what it finds into the Person: values (an occupation, a city, an age), what they did and said (episodes with their own quoted words), and facts. One file can feed several people: a survey export gives one Person per respondent, a recording with four speakers can give four.

What each source gave is kept, per Person, and you can read it back:

- in the app, on the Person's **Sources** tab;
- in the CLI, `ish person get <id> --sources`: each file, what it gave (values, conversations, facts), and how many people in the workspace it feeds;
- in MCP, `person_get(person_id=…, include=["sources"])`.

Every value on a Person also says where it came from: a source, your brief, or ish.

<Note>
A source grounds a simulated person; it does not turn the output into a real human. A Person built from a real transcript is closer to the mark than one built from a prompt, but it is still simulation. Frame the findings the same way.
</Note>

## Why you may share it

Every hand-in of material says why you may share it: the people in it agreed, it is public, it comes from your work with them, or you made it (`remembered` reuses your last answer for a Person you are adding to). It is stored with the hand-in as your word, not the person's consent. Say also when other people are in the material too. At a terminal the CLI asks; without one, `--basis` is required, and an agent asks its human rather than choosing. In MCP the same reason is `rights_basis`.

## Source kinds

Every source is one of three kinds, detected from the file extension or MIME type:

| Kind | What it covers |
|---|---|
| `text_file` | PDF, Excel (`.xlsx`), CSV and TSV, plain text, Markdown, email (`.eml`), captions (`.vtt`, `.srt`) |
| `audio` | recordings (`.mp3`, `.wav`, `.m4a`, `.ogg`, `.mp4`, `.mov`, `.webm`), transcribed with speakers told apart |
| `image` | `.png`, `.jpg`, `.jpeg`, `.webp` |

Word documents are read only as PDF: export the file as PDF and hand in the PDF. JSON and HTML files are not parsed, so convert them to PDF or plain text first.

## Two ways to use a source

<Columns cols={2}>
  <Card title="Inline" icon="bolt">
    Hand a local file straight to a build. It is uploaded for that hand-in. Reach for this when the file belongs to one build.
  </Card>
  <Card title="Upload then reuse" icon="recycle">
    Upload the file once, get an id back, and reference it from several builds without re-uploading.
  </Card>
</Columns>

Inline is the common path. In the CLI, `ish person build ./call.mp3 --basis agreed` uploads the file and hands it in. In MCP, `person_build(sources=[{"path": …}], rights_basis="agreed")` does the same; a source can also be pasted text (`text`) or raw bytes (`inline_base64` with a `file_name`).

Upload then reuse separates the upload into its own step. `ish source upload` returns a `ps-` alias you pass as `ish person build --source ps-…`. The MCP `source_upload` tool returns a `source_upload_id` you pass as `person_build(source_upload_ids=[…])`.

<Tip>
The note that captures how a real person reacted (`--description` on `ish source upload`, `reaction` on `source_upload`) is set at upload time and travels with the file.
</Tip>

## Where the bytes come from

The CLI reads sources from your local filesystem. The MCP server runs the upload on its own machine, so it accepts three input shapes:

- a path the **MCP process** can read on its filesystem,
- an `http(s)://` URL, fetched server-side (SSRF-guarded, with a 10 MB cap),
- a `data:` URL, or raw `inline_base64` bytes with a `file_name`, for hosted clients that can pass bytes but not a path.

This matters when an agent runs against the hosted MCP server: a path that exists on your laptop is not on the server, so pass the bytes or a reachable URL instead.

## Processing and status

A source is not ready the instant the bytes land. After the upload, ish processes it: text and images are parsed, audio is transcribed. A source moves toward one of two terminal states, `processed` or `failed`. A build waits for processing itself; the standalone CLI upload polls until the source is terminal, with `--no-wait` to return early.

A `failed` source carries an error you can read back. Inspect any uploaded source by id with `ish source get`.

## How a source lives over time

A source outlives the build that read it. Deletes are ref-counted: `ish source delete` removes the source and its file only when no Person still links to it, so deleting a source never silently rewrites the people it fed. In the app, a file can be erased from one Person or for everyone it feeds, after a list of exactly what goes.

The alias prefix differs by surface. The CLI tags a source with a `ps-` alias; the MCP server uses `tps-` for the same family of attachments. Both resolve to the same underlying file. Use whichever prefix the surface you are on returns.
